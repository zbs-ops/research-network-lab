# 長距離・高帯域ネットワークでの TCP チューニング検証（要約）

*Zohaib Qamar、2026年11月。コード・生データ・全 CI 実行ログ: github.com/zbs-ops/research-network-lab*

研究機関のキャンパス間や海外の連携機関との間で大容量データを転送する場面を想定し、往復遅延（RTT）とわずかなパケットロスが TCP 転送性能にどう影響するかを、エミュレーション環境で測定しました。なお、この検証環境の構築と実行は、私が指示する AI エージェント（Friday）が行いました。問いの設定、ルール（すべての数値を誰でも開ける CI 実行に紐づける、環境の確認結果を先に示す、失敗を記録する）、各フェーズの承認は私が担当しています。

**環境:** GitHub Actions の無料ランナー（2 vCPU、7,932 MB RAM）上で、2つのネットワーク名前空間を veth で接続し、`tc netem` で遅延・ロスと 1 Gbit/s のボトルネックを再現しました。RTT は 10 ms・120 ms・250 ms、各条件を2回の CI 実行で計6回測定しています（数値は中央値、Mbit/s）。

**主な結果:**

- **ロス率 0.1% では輻輳制御の差が決定的です。** RTT 250 ms のとき、CUBIC は 33、BBR は 707 でした。ロスがない場合、両者の差は数パーセント以内です。
- **既定のソケットバッファが長距離転送を制限します。** ロスなし・RTT 250 ms で、Ubuntu の既定値では 81、上限を 256 MB に引き上げると 791 になりました。
- **ジャンボフレーム（MTU 9000）の効果はヘッダ比率の計算どおりでした。** RTT 10 ms で 952 → 989（理論値 956 → 993）。
- **BBR を4本並列にすると、RTT 250 ms で転送が止まることがありました。** 原因を追跡したところ、BBR の起動時のオーバーシュートでカーネルの TCP メモリが `tcp_mem` の圧迫しきい値に達し、受信側の広告ウィンドウが約 0.6 MB（正常時は約 100 MB）まで縮小していました。`tcp_mem` の上限を4倍にした対照実験では、停止は 12回中0回となりました（通常設定では 34回中10回、片側 Fisher 正確検定 p = 0.03）。バッファを大きくする際は `tcp_mem` とメモリ量も合わせて見直す必要があります。

あわせて、FRRouting による leaf-spine ファブリック（eBGP unnumbered、BFD、ECMP）と、Prometheus・Grafana による監視も構築しました。BGP セッションは正常なまま経路だけが消える設定ミスを、経路の有無を見るアラートが 3.5〜5.5 秒で検知し、セッション監視のアラートは発報しませんでした。

制約: 1台のクラウド VM 上のエミュレーションであり、実回線の並べ替え、遅延変動、バースト性のロス、競合トラフィックは再現していません。詳細と生データはリポジトリにあります。
